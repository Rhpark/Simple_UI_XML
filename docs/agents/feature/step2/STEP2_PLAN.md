# STEP2. 계획 문서 작성

목적: PRD·SPEC·PLAN 세 문서를 작성해 구현 기준선을 확정한다. 이 단계의 산출물이 STEP4 마일스톤 루프에서 하네스 판정 기준으로 사용된다.

이 STEP은 Tier A에서만 실행한다. Tier B는 STEP2를 건너뛰고 STEP3으로 직행한다.

## 진입 조건

- STEP1 하네스를 통과했다
- STEP1 산출물에서 아래 항목이 전달됐다
  - [ ] `Tier` — A로 확정됐다
  - [ ] `분기` — A·B·C 중 하나와 사용할 산출물 경로가 기록됐다
  - [ ] `직접 파일` — 파일명:라인번호 형식으로 기록됐다
  - [ ] `간접 파일` — 기록됐거나 "없음"으로 확인됐다
  - [ ] `출력 디렉토리` — `docs/agents/output/feature/YYYYMMDD_HHmmss/` 경로가 확정됐다

## 행동 원칙

- 분기 A·B에서 기반 자료를 직접 열어 확인한 내용만 PRD·SPEC·PLAN에 반영한다.
- 기반 자료에 없는 내용을 추정으로 채우지 않는다. 필요한 결정은 사용자에게 확인한다.
- PRD·SPEC·PLAN 세 문서 간 내용이 충돌하면 사용자에게 확인 후 해소한다.
- 마일스톤은 각각 독립적으로 빌드·테스트 가능한 단위로 나눈다.

## 실행 체크리스트

- [ ] 1. STEP1 산출물에서 입력값을 확인한다 (Tier, 분기, 직접 파일, 출력 디렉토리).

- [ ] 2. 분기에 따라 기반 자료를 수집한다.
  - **분기 A** (review 산출물 있음): STEP1이 기록한 review 산출물 파일을 연다.
    → review 산출물에서 참조할 내용: 발견 사항(findings), 기능 검증 결과, 아키텍처 확인 결과
  - **분기 B** (analysis 산출물만 있음): STEP1이 기록한 analysis 산출물 파일을 연다.
    → analysis 산출물에서 참조할 내용: 직접 파일, 원인 목록, 사용자 영향
  - **분기 C** (산출물 없음): STEP1의 직접 파일을 직접 열어 수정 맥락을 파악한다.
  → 분기 A·B에서 지정 파일을 열 수 없으면 강제 중단 조건 적용.

- [ ] 3. 아래 형식에 맞춰 PRD.md를 작성하고 출력 디렉토리에 저장한다.

  **PRD.md 필수 섹션:**

  ```markdown
  # PRD — [기능명]

  ## 기능 목적
  [외부에서 관찰 가능한 동작 기대치. "무엇을 하는가"만 기록한다. 구현 방식은 SPEC으로]

  ## 금지 패턴
  [구현 시 사용해서는 안 되는 패턴 목록. STEP4 마일스톤마다 준수 여부를 확인한다]
  - 금지: [패턴명 — 금지 이유]

  ## 경계 조건
  - 책임 범위: [이 기능이 담당하는 것]
  - 책임 외 범위: [이 기능이 담당하지 않는 것]
  ```

  → 금지 패턴이 없으면 "없음"으로 명시한다.

- [ ] 4. 아래 형식에 맞춰 SPEC.md를 작성하고 출력 디렉토리에 저장한다.

  **SPEC.md 필수 섹션:**

  ```markdown
  # SPEC — [기능명]

  ## 판단 기준
  [구현 결정 시 따르는 기준. 설계 선택의 근거로 사용한다. STEP4 마일스톤마다 기준 준수를 확인한다]
  - [결정 상황]: [선택 기준 — 이유]

  ## 설계 선택
  [이 구현에서 선택한 설계 방식과 이유]
  - [선택 항목]: [선택 내용 — 근거]

  ## 인터페이스 정의
  [공개 API 추가·변경이 있으면 기록한다. 없으면 "없음"]
  ```

- [ ] 5. 아래 형식에 맞춰 PLAN.md를 작성하고 출력 디렉토리에 저장한다.

  **PLAN.md 필수 섹션:**

  ```markdown
  # PLAN — [기능명]

  ## 마일스톤 목록

  표는 순서와 이름만 담는다. 수정 파일·기준선 상세는 아래 각 마일스톤 섹션에 기술한다.

  | 순서 | 마일스톤명 |
  |---|---|
  | 1 | [이름] |

  ---

  ### 마일스톤 N. [이름]

  **목적**: [이 마일스톤에서 달성하는 것]
  **수정 파일**: 파일명:라인번호
  **기준선**: [빌드 통과 / 특정 테스트 통과 / 특정 동작 확인 등 완료 판정 조건]
  ```

  마일스톤 분리 기준:
  - 각 마일스톤은 독립 빌드·테스트로 검증 가능해야 한다
  - 한 마일스톤이 실패해도 이전 마일스톤 결과는 유효해야 한다
  - 기준선 없는 마일스톤은 작성하지 않는다

- [ ] 6. PRD·SPEC·PLAN 세 문서 간 일관성을 검증한다.
  - PRD 금지 패턴이 PLAN 마일스톤 구현과 충돌하지 않는가
  - PRD 경계 조건이 PLAN 전체 범위와 일치하는가
  - SPEC 판단 기준이 PLAN 설계 선택에 반영됐는가
  → 충돌 발견: 사용자에게 확인 요청 후 해소한다.

- [ ] 7. 산출물 형식에 맞춰 출력한다.

## 하네스

- [ ] 1번 통과 — STEP1 입력값이 전부 확인됐고 Tier A가 확정됐다.
     **CRITICAL** / 미통과 시: Tier B이면 이 STEP을 건너뜀 — 실행하지 않는다. STEP1 산출물이 불완전하면 STEP1로 복귀.
- [ ] 2번 통과 — 분기에 맞는 기반 자료가 수집됐다.
     **HIGH** / 미통과 시: 분기 A·B에서 파일 열기 실패이면 강제 중단. 분기 C이면 직접 파일 스캔으로 재수행.
- [ ] 3번 통과 — PRD.md가 출력 디렉토리에 생성됐고 필수 섹션(기능 목적·금지 패턴·경계 조건)이 있다.
     **CRITICAL** / 미통과 시: 3번 재수행.
- [ ] 4번 통과 — SPEC.md가 출력 디렉토리에 생성됐고 필수 섹션(판단 기준·설계 선택·인터페이스 정의)이 있다.
     **CRITICAL** / 미통과 시: 4번 재수행.
- [ ] 5번 통과 — PLAN.md가 출력 디렉토리에 생성됐고 마일스톤이 1개 이상이며 각 마일스톤에 기준선이 있다.
     **CRITICAL** / 미통과 시: 마일스톤 0개이면 강제 중단. 기준선 누락이면 5번 재수행.
- [ ] 6번 통과 — 세 문서 간 충돌이 없거나 사용자 확인으로 해소됐다.
     **HIGH** / 미통과 시: 충돌 항목을 사용자에게 전달하고 해소 후 재수행.
- [ ] 7번 통과 — 산출물이 형식에 맞춰 출력됐다.
     **HIGH** / 미통과 시: 7번 재수행.

미통과 항목이 있으면 실패 규격에 따라 기록 후 강제 중단 조건을 확인한다. 루프 판정 기준은 → [STEP_ROLLBACK.md](../../common/STEP_ROLLBACK.md) 참조

## 사용자 검증 포인트

AI 산출물 수령 후 아래 항목을 확인한다.

- [ ] PRD `금지 패턴`이 실제로 피해야 할 구현 방식과 맞는가
- [ ] PRD `경계 조건`이 요청 범위를 정확히 반영하는가 — 너무 넓거나 좁지 않은가
- [ ] SPEC `판단 기준`이 실제 구현 결정에서 따를 수 있는 기준인가
- [ ] PLAN `마일스톤 목록`이 논리적 순서인가 — 앞 마일스톤이 뒤 마일스톤의 전제 조건을 만족하는가
- [ ] PLAN 각 마일스톤의 `기준선`이 실제로 검증 가능한 조건인가

## 실패 규격

하네스 미통과 시 아래 형식으로 기록한다.

```text
실패 STEP   : STEP2
실패 항목   : 미통과 하네스 항목명
실패 원인   : 어떤 데이터가 없는지 / 어떤 조건이 충족되지 않는지
복귀 대상   : 해당 체크리스트 항목
전달 데이터 : PRD 경로 / SPEC 경로 / PLAN 경로 / 마일스톤 목록 / 이슈. 미완성 항목은 "미완성"
```

## 강제 중단 조건

복귀 없이 즉시 작업을 멈춘다.

- 분기 A·B에서 지정 산출물 파일을 열 수 없고 사용자 재확인 후에도 해소되지 않는다 → 작업 중단
- 마일스톤을 1개도 도출할 수 없다 → 사용자에게 수정 범위 재정의 요청 후 중단
- 세 문서 간 충돌이 사용자 확인 후에도 해소되지 않는다 → 작업 중단
- 루프 판정 → [STEP_ROLLBACK.md](../../common/STEP_ROLLBACK.md) 루프 판정 기준 적용
