# STEP1. 진입 판정

목적: 수정 범위를 파악해 Tier를 확정하고, 사전 컨텍스트(analysis·review 산출물) 존재 여부로 분기를 결정한다. 출력 디렉토리 경로를 이 단계에서 확정한다.

## 진입 조건

- 사용자 요청이 있다.
- 아래 중 하나 이상을 식별할 수 있다.
  - 수정할 기능명
  - 수정할 파일명 또는 클래스명
  - 버그 증상 또는 오류 문구
  - 화면명 또는 사용자 행동

## 행동 원칙

- 직접 파일을 열거나 빠른 스캔으로 확인한 사실만 Tier 판정 근거로 사용한다.
- 확인하지 않은 파일을 "영향받을 것"으로 추정해 Tier를 높이지 않는다.
- 분기 판정은 실제 경로를 확인한 결과만 사용한다.
- Tier B 판정 후 구현 중 복잡도가 Tier A 수준으로 드러나면 즉시 STEP1로 복귀해 재판정한다.

## 실행 체크리스트

- [ ] 1. 요청이 feature 워크플로우 범위(외부 동작 변경을 수반하는 코드 수정)인지 판정한다.
  → 범위 밖(분석만·리뷰만·리팩토링만): 강제 중단 조건 적용.
  → 범위 내: 2번으로 진행한다.

- [ ] 2. 수정 대상 파일(직접 파일)을 식별한다. 파일명:라인번호 형식으로 목록화한다.
  - 요청에 파일명이 명시됐으면 해당 파일을 직접 열어 확인한다.
  - 기능명·화면명·클래스명만 있으면 Glob·Grep으로 진입점 파일을 찾는다.
  → 식별 불가: 사용자에게 수정 대상 파일 또는 기능명 확인을 요청하고 대기한다.

- [ ] 3. 아래 기준으로 Tier를 판정하고 판정 근거를 기록한다.

  **Tier B 판정 기준** (아래 조건을 모두 충족):
  - 단일 파일 또는 단일 클래스 내 수정
  - 기존 패턴 그대로 사용 (새 클래스·인터페이스 추가 없음)
  - 공개 API 변경 없음 (추가·변경·제거 모두 해당)
  - 복수 레이어 걸치지 않음

  **Tier A 판정 기준** (아래 중 하나라도 해당):
  - 복수 파일·클래스 수정 또는 새 파일 생성
  - 공개 API 추가·변경·제거
  - 복수 레이어 걸침 (예: ViewModel + Repository + DataSource)
  - 새 기능 시나리오 추가
  - 기존 동작(behavior) 변경

  → 판정 근거가 모호하면 Tier A로 보수 판정한다.

- [ ] 4. Tier A인 경우 분기를 판정한다. Tier B는 이 항목을 건너뛴다.
  - `docs/agents/output/review/` 디렉토리에 `.md` 파일이 있으면 → **분기 A**
    → 사용자가 파일을 명시했으면 해당 파일을, 명시 없으면 가장 최신 파일을 사용한다.
  - review 산출물 없고 `docs/agents/output/analysis/` 디렉토리에 `.md` 파일이 있으면 → **분기 B**
    → 사용자가 파일을 명시했으면 해당 파일을, 명시 없으면 가장 최신 파일을 사용한다.
    → 분기 B: review 실행을 권고하고, 사용자가 계속 진행을 선택하면 분기 B로 진행한다.
  - 둘 다 없으면 → **분기 C**
    → 분기 C: analysis·review 실행을 권고하고, 사용자가 계속 진행을 선택하면 분기 C로 진행한다.

- [ ] 5. 직접 파일 수정으로 함께 변경이 필요한 간접 파일을 식별한다.
  - 직접 파일의 호출자·구현체·테스트 파일·의존 문서를 확인한다.
  → 없으면 "없음"으로 기록한다.

- [ ] 6. 출력 디렉토리 경로를 확정한다.
  - 형식: `docs/agents/output/feature/YYYYMMDD_HHmmss/`
  - 현재 날짜·시간으로 경로를 생성하고 기록한다.

- [ ] 7. 산출물 형식에 맞춰 출력한다.

## 하네스

- [ ] 1번 통과 — feature 범위 여부가 판정됐고, 범위 밖이면 강제 중단이 적용됐다.
     **CRITICAL** / 미통과 시: 1번 재수행. 범위 밖을 진행한 경우 즉시 중단.
- [ ] 2번 통과 — 직접 파일이 1개 이상 식별됐고 파일명:라인번호 형식으로 기록됐다.
     **CRITICAL** / 미통과 시: 식별 불가이면 사용자 질문 후 대기. 누락이면 2번 재수행.
- [ ] 3번 통과 — Tier가 A 또는 B로 판정됐고 판정 근거가 기록됐다.
     **CRITICAL** / 미통과 시: 모호하면 Tier A로 보수 판정하고 근거 기록 후 통과. 근거 없으면 3번 재수행.
- [ ] 4번 통과 — Tier A이면 분기(A·B·C)가 판정됐고 사용할 산출물 경로가 기록됐다. Tier B이면 자동 통과.
     **HIGH** / 미통과 시: 4번 재수행.
- [ ] 5번 통과 — 간접 파일이 기록됐거나 "없음"이 확인됐다.
     **MEDIUM** / 미통과 시: 5번 재수행.
- [ ] 6번 통과 — 출력 디렉토리 경로가 확정됐다.
     **HIGH** / 미통과 시: 6번 재수행.
- [ ] 7번 통과 — 산출물이 형식에 맞춰 출력됐다.
     **HIGH** / 미통과 시: 7번 재수행.

미통과 항목이 있으면 실패 규격에 따라 기록 후 강제 중단 조건을 확인한다. 루프 판정 기준은 → [STEP_ROLLBACK.md](../../common/STEP_ROLLBACK.md) 참조

## 산출물(다음 STEP에 전달 정보)

STEP 완료 시 아래 형식으로 값을 채워 출력한다.

```text
[feature workflow — STEP1 산출물]
단계     : STEP 1 (진입 판정)
진행도   : (n/7) - 마지막으로 완료한 체크리스트 항목명 (진행중 / 완료)

Tier            : A 또는 B — 판정 근거
분기            : A·B·C 중 하나 — 사용할 산출물 경로. Tier B이면 "해당 없음"
직접 파일       : 파일명:라인번호 (복수이면 목록)
간접 파일       : 파일명:라인번호. 없으면 "없음"
STEP2 적용 여부 : Tier A → 필수 / Tier B → 생략
출력 디렉토리   : docs/agents/output/feature/YYYYMMDD_HHmmss/

이슈 : [Tier/분기/파일/기타] 내용 — 이유. 없으면 "없음"
```

→ 출력 예시는 [STEP1_SAMPLES.md](STEP1_SAMPLES.md) 참조

## 사용자 검증 포인트

AI 산출물 수령 후 아래 항목을 확인한다.

- [ ] `Tier` 판정이 실제 수정 범위와 맞는가 — 더 단순하거나 더 복잡한 판정이 아닌가
- [ ] `직접 파일`이 실제 수정 대상과 일치하는가 — 누락되거나 잘못 포함된 파일은 없는가
- [ ] Tier A이면 `분기` 판정이 실제 산출물 파일 존재와 일치하는가
- [ ] 분기 B·C이면 권고에 따라 review·analysis를 먼저 실행할지 직접 결정한다
- [ ] `이슈`가 "없음"이 아니면, 진행 여부를 직접 결정한다


## 강제 중단 조건

복귀 없이 즉시 작업을 멈춘다.

- 요청이 feature 범위 밖이다 → 사용자에게 적절한 워크플로우 안내 후 중단
- 직접 파일을 식별할 수 없고 사용자 질문 후에도 해소되지 않는다 → 작업 중단
- Tier 판정이 불가능하고 사용자 질문 후에도 해소되지 않는다 → 작업 중단
- 루프 판정 → [STEP_ROLLBACK.md](../../common/STEP_ROLLBACK.md) 루프 판정 기준 적용
