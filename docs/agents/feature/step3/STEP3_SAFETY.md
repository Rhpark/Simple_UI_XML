# STEP3. 안전망 확보

목적: 구현 시작 전 빌드·테스트·API 현황을 기록해 STEP5 회귀 비교의 기준선을 확정한다.

이 STEP은 Tier A·B 모두 실행한다.
- Tier A: STEP2 완료 후 진입한다.
- Tier B: STEP1 완료 후 STEP2를 건너뛰고 진입한다.

## 진입 조건

**Tier A 진입 시:**
- STEP2 하네스를 통과했다
- STEP2 산출물에서 아래 항목이 전달됐다
  - [ ] `PRD 경로` — 파일이 실제로 존재한다
  - [ ] `SPEC 경로` — 파일이 실제로 존재한다
  - [ ] `PLAN 경로` — 파일이 실제로 존재한다
  - [ ] `마일스톤 목록` — 1개 이상 기록됐다

**Tier B 진입 시:**
- STEP1 하네스를 통과했다
- STEP1 산출물에서 아래 항목이 전달됐다
  - [ ] `직접 파일` — 파일명:라인번호 형식으로 기록됐다
  - [ ] `출력 디렉토리` — 경로가 확정됐다

## 행동 원칙

- 빌드·테스트 실행 결과를 있는 그대로 기록한다. 통과/실패를 판단하지 않고 기록이 목적이다.
- 기존 실패(구현 전부터 있던 실패)와 신규 실패를 구분할 수 있도록 현재 상태를 명확히 기록한다.
- 빌드 실패 원인이 직접 파일과 연관되면 사용자에게 보고 후 진행 여부를 결정받는다.
- API 스냅샷 실행이 불가한 경우 이유를 기록하고 진행한다.

## 실행 체크리스트

- [ ] 1. 진입 조건 항목을 확인한다. 직접 파일 경로에서 대상 모듈명을 추출한다.
  - 모듈명 추출 기준: 직접 파일 경로의 첫 번째 세그먼트 (예: `simple_xml/src/...` → `simple_xml`)
  - 복수 모듈에 걸친 경우 모든 모듈명을 목록화한다.

- [ ] 2. 대상 모듈의 빌드를 실행하고 결과를 기록한다.
  - 실행 명령 (PowerShell):
    ```
    powershell -Command "cd 'D:\Android Project\SimpleUI_XML'; .\gradlew.bat :[모듈명]:assembleDebug"
    ```
  - 결과 기록: 통과 / 실패(오류 메시지 포함)
  - 실패 시: 오류가 직접 파일과 연관되는지 판단한다.
    → 연관됨: 사용자에게 보고하고 진행 여부를 결정받는다.
    → 연관 없음(기존 실패): "기존 실패 — [오류 요약]"으로 기록하고 계속 진행한다.

- [ ] 3. 대상 모듈의 테스트를 실행하고 결과를 기록한다.
  - 실행 명령 (PowerShell):
    ```
    powershell -Command "cd 'D:\Android Project\SimpleUI_XML'; .\gradlew.bat :[모듈명]:testRobolectric :[모듈명]:testUnit"
    ```
  - 결과 기록: 통과 수 / 실패 테스트명 목록. 실패가 없으면 "없음".
  - 이 목록이 STEP5 테스트 기준선으로 사용된다. 구현 후 새로 실패한 테스트를 여기서 비교한다.

- [ ] 4. API 스냅샷을 실행하고 결과를 기록한다.
  - 실행 명령 (PowerShell):
    ```
    powershell -Command "cd 'D:\Android Project\SimpleUI_XML'; .\gradlew.bat apiDump"
    ```
  - 결과 기록: 공개 API 목록 요약. 이 목록이 STEP5 `apiCheck` Breaking Change 판별 기준이 된다.
  - 실행 불가 시: 이유를 기록하고 `API 스냅샷 : 미실행 — [이유]`로 명시한 뒤 진행한다.

- [ ] 5. 산출물 형식에 맞춰 출력한다.

## 하네스

- [ ] 1번 통과 — 진입 조건이 확인됐고 대상 모듈명이 추출됐다.
     **CRITICAL** / 미통과 시: Tier A이면 PRD·SPEC·PLAN 파일 존재 확인 후 재수행. Tier B이면 직접 파일 확인 후 재수행.
- [ ] 2번 통과 — 빌드 기준선이 기록됐다. 통과·실패 중 하나로 명시됐다.
     **HIGH** / 미통과 시: 빌드 실행 재수행. 직접 파일 연관 실패이면 사용자 확인 후 진행.
- [ ] 3번 통과 — 테스트 기준선이 기록됐다. 통과 수와 실패 목록이 명시됐다.
     **MEDIUM** / 미통과 시: 테스트 실행 재수행. 실행 불가이면 이유 기록 후 자동 통과.
- [ ] 4번 통과 — API 스냅샷이 기록됐거나 미실행 이유가 명시됐다.
     **MEDIUM** / 미통과 시: apiDump 재실행. 재실행 불가이면 이유 기록 후 자동 통과.
- [ ] 5번 통과 — 산출물이 형식에 맞춰 출력됐다.
     **HIGH** / 미통과 시: 5번 재수행.

미통과 항목이 있으면 실패 규격에 따라 기록 후 강제 중단 조건을 확인한다. 루프 판정 기준은 → [STEP_ROLLBACK.md](../../common/STEP_ROLLBACK.md) 참조

## 사용자 검증 포인트

AI 산출물 수령 후 아래 항목을 확인한다.

- [ ] `빌드 기준선`이 실제 빌드 결과를 반영하는가 — 실패이면 직접 파일 연관 여부를 직접 확인한다
- [ ] `테스트 기준선`의 실패 목록이 기존에 알고 있던 실패와 일치하는가 — 예상 밖의 실패가 있으면 원인을 확인한다
- [ ] `API 스냅샷`이 미실행이면 STEP5 apiCheck를 건너뛰게 됨을 인지한다
- [ ] `빌드 기준선`에 "기존 실패"가 있으면 STEP5에서 해당 실패는 회귀로 판정하지 않는다 — 이를 인지하고 있는가
