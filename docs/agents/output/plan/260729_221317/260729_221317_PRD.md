# 다음 메이저 공개 API 정리 PRD

**상태**: 확정

## 1. 개요
- `simple_system_manager`의 공개 API 감사 후보 중 사용자가 확정한 5개 Breaking Change를 다음 메이저 범위로 통합 관리한다.
- 구현은 후보별 독립 배치로 나누어 검증하고, 소비자 대체 경로와 릴리스 변경 사항을 함께 제공한다.

## 2. 변경 배경
- 현재 공개 API에는 동일 기능의 호환 별칭, XML 계층에서만 사용하는 Core 확장, 내부 구현 성격의 공개 타입과 생성 API가 포함되어 있다.
- 현 버전에서는 기존 소비자 호환성을 위해 공개 ABI를 유지했으므로, 실제 표면 축소는 Breaking Change가 허용되는 다음 메이저에서 수행해야 한다.
- 공개 API를 한 번에 임의 삭제하지 않고 감사 결과와 대체 경로를 기준으로 단계적으로 정리할 필요가 있다.

## 3. 현재 상태
- `getSystemNotificationManager()`와 `getNotificationManager()`가 함께 공개되어 있으며 전자는 후자에 위임한다.
- `getWindowManager()`와 `getInputMethodManager()`는 Core 확장에 있지만 운영 사용처는 XML 계층에 한정된다.
- `PowerProfile`, `PowerProfileVO`, `CommonTelephonyCallback`, `TelephonyCallbackManager`는 공개 ABI에 남아 있다.
- `NetworkBase`는 두 공개 연결성 데이터 타입의 공개 상위 클래스이며 사용자 결정에 따라 이 계약을 유지한다.
- 라이브러리 `BuildConfig`가 생성되어 공개 API 기준선에 포함된다.

## 4. 목표 상태
- 중복 호환 별칭 `getSystemNotificationManager()`를 공개 API에서 제거하고 `getNotificationManager()`를 대표 API로 유지한다.
- `getWindowManager()`와 `getInputMethodManager()`를 Core 공개 API에서 제거하고 XML 계층 내부 접근 경로로 정리한다.
- 내부 구현 타입인 `PowerProfile`, `PowerProfileVO`, `CommonTelephonyCallback`, `TelephonyCallbackManager`를 공개 API에서 제거한다.
- `NetworkBase`와 두 공개 연결성 데이터 타입의 상속 계약을 현행대로 유지한다.
- 라이브러리 `BuildConfig` 생성을 비활성화하고 공개 API 기준선에서 제거한다.
- 모든 제거 항목에 소비자 대체 경로와 Breaking Change 안내를 제공한다.

## 5. 변경 범위
- In scope:
  - `getSystemNotificationManager()` 제거
  - `getWindowManager()`, `getInputMethodManager()`의 공개 Core 확장 제거와 XML 내부 경로 정리
  - `PowerProfile`, `PowerProfileVO` 내부화
  - `CommonTelephonyCallback`, `TelephonyCallbackManager` 내부화
  - 라이브러리 `BuildConfig` 생성 비활성화
  - 공개 API 기준선, 소비자 문서, 마이그레이션 및 릴리스 문서 갱신
  - 각 배치의 테스트와 정적 분석
- Out of scope:
  - 다음 메이저의 구체적인 버전 번호와 출시 일정 확정
  - 새 시스템 서비스 기능 또는 새 공개 API 추가
  - 위 후보와 무관한 기존 동작·반환값 변경
  - `NetworkBase`, `NetworkCapabilitiesData`, `NetworkLinkPropertiesData`의 공개 상속 계약 변경
  - 현 호환 버전에서 공개 API를 선제 삭제
  - 다른 모듈의 공개 API 정리

## 6. 영향 범위 (사용자·기능 관점)
- 제거 대상 API를 직접 사용하는 소비자는 다음 메이저 적용 시 대체 API로 이동해야 한다.
- 대표 Controller·Info 진입점과 XML 확장 5개는 유지되므로 일반적인 기능 사용 흐름은 유지된다.
- `NetworkBase`를 직접 상속하거나 타입으로 사용하는 소비자 코드는 영향을 받지 않는다.
- 라이브러리 `BuildConfig`를 참조한 소비자는 자신의 앱·모듈 빌드 설정을 사용해야 한다.
- 각 배치를 독립 검증하여 한 후보의 실패가 다른 후보의 적용 여부를 가리지 않도록 한다.

## 7. 제약
- 공개 API 삭제와 내부화는 다음 메이저에서만 수행한다.
- 현 버전의 공개 ABI와 기존 테스트 기준선을 구현 시작 전 기준으로 보존한다.
- 이미 안내된 대체 경로를 우선 사용하며 대체 목적만을 위한 새 공개 API는 추가하지 않는다.
- 사용자 결정에 따라 새 Deprecated 표시는 추가하지 않는다.
- 기능 동작 변경 없이 공개 표면과 계층 책임만 정리한다.
- UTF-8과 한글 문서 품질을 유지하고 각 배치 후 글자 깨짐을 검수한다.

## 8. 성공 조건
- 5개 후보가 승인된 배치 순서에 따라 구현되고 후보별 검증 결과가 기록된다.
- 제거 대상이 다음 메이저 공개 API 기준선에 남지 않는다.
- 유지 대상 Controller·Info·XML 확장의 공개 시그니처와 기능 동작이 보존된다.
- `NetworkBase`, `NetworkCapabilitiesData`, `NetworkLinkPropertiesData`의 공개 상속 관계가 API 기준선에 유지된다.
- 각 제거 항목의 대체 경로가 README 또는 마이그레이션 문서에 명시된다.
- `simple_system_manager`의 Unit·Robolectric 테스트, 정적 분석과 API 검증이 모두 통과한다.
- 소비자 예제와 실기기 검증 코드가 제거된 API를 참조하지 않는다.
- Breaking Change 목록이 릴리스 문서에 기록된다.

## 9. 리스크
- 공개 API를 직접 사용하는 외부 소비자의 빌드가 깨질 수 있다.
- Telephony 콜백 내부화 과정에서 SDK별 등록·해제 경로가 달라질 수 있다.
- `BuildConfig` 비활성화 시 테스트와 빌드 변형별 조건 분기가 실패할 수 있다.
- Core/XML 접근자 이동 과정에서 패키지 의존 방향이 역전될 수 있다.
- 여러 Breaking Change를 한 번에 적용하면 회귀 원인 추적이 어려울 수 있으므로 독립 배치 검증이 필요하다.

## 10. 미해결 이슈
- 없음. 구체적인 다음 메이저 버전 번호와 출시 일정은 이 PRD 범위에서 확정하지 않는다.
