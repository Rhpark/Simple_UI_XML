# 실기기 검증 체계 SPEC

## 문서 정보

- 문서명: 실기기 검증 체계 SPEC
- 대상 프로젝트: Simple UI
- 대상 모듈: `simple_core`, `simple_system_manager`, `simple_compose`, `simple_xml`, `app`
- 상태: Draft
- 상위 요구사항: [PRD.md](./PRD.md)
- 구현 계획: [IMPLEMENTATION_PLAN.md](./IMPLEMENTATION_PLAN.md)

## 문서 목적

이 문서는 PRD에서 정의한 실기기 검증 체계를 실행 가능한 규격으로 구체화합니다. 1단계 범위인 전용 실기기 통합 테스트, 수동 시나리오, 우선순위, 결과 기록, 예외 승인 및 릴리스 차단 조건을 정의합니다.

## 적용 단계

### 1단계: 현재 SPEC의 필수 범위

- 전용 테스트 단말 한 대를 기준 기기로 등록합니다.
- `app/src/androidTest`에 네 라이브러리 모듈의 통합 테스트를 구축합니다.
- 자동화가 부적절한 기능은 샘플 앱을 이용한 수동 또는 혼합 시나리오로 검증합니다.
- 검증 결과를 릴리스별 Markdown 문서로 기록합니다.
- 네 모듈의 검증 체계가 모두 준비되면 실기기 검증을 릴리스 차단 조건으로 활성화합니다.

### 2단계: 후속 범위

- API 28·33·35 에뮬레이터 매트릭스
- CI의 에뮬레이터 계측 테스트 자동 실행
- 추가 제조사 단말, 실제 SIM 단말 또는 기기 팜
- 다중 단말 결과 집계와 자동 승인 게이트

2단계 항목은 이번 SPEC의 1단계 완료 조건이나 최초 릴리스 차단 활성화 조건에 포함하지 않습니다.

## 검증 대상 기준

### 기준 단말 슬롯

| 항목 | 값 |
| --- | --- |
| 슬롯 ID | `PHY-01` |
| 용도 | 전용 테스트 단말 |
| 제조사·모델 | Samsung `SM-G977N` |
| 단말 일련번호 | `R3CM50A575V` |
| Android 버전 | Android 12 |
| API | 31 |
| ABI | `arm64-v8a` |
| SIM 상태 | 없음 |
| 주요 사용 가능 기능 | Wi-Fi, 전화 서비스, 위치·GPS, Bluetooth, NFC, 센서 |

- 표의 단말 정보는 현재 슬롯 할당값입니다. 단말 교체 시 슬롯 ID는 유지하고 할당값과 변경 사유를 갱신합니다.
- 실제 릴리스 결과에는 실행 시점의 보안 패치 수준, 네트워크 상태, SIM 상태 및 배터리 상태를 다시 기록합니다.
- 일련번호가 다르거나 API가 변경된 단말은 동일 슬롯으로 자동 간주하지 않습니다. SPEC 또는 릴리스 결과에 변경 근거를 남깁니다.

### 실행 전 조건

- `adb devices -l`에서 `PHY-01`에 등록된 일련번호가 `device` 상태여야 합니다.
- 릴리스 승인용 전체 실행 시에는 `PHY-01`만 연결하여 다른 단말에서 테스트가 함께 실행되지 않도록 합니다.
- 배터리는 30% 이상이어야 하며 절전 모드 적용 여부를 기록합니다.
- Wi-Fi 연결 상태와 위치·알림·정확한 알람·오버레이 등 검증 관련 설정의 초기 상태를 기록합니다.
- 이전 검증이 남긴 알림, 알람, 플로팅 뷰 및 앱 데이터가 결과에 영향을 주지 않도록 정리합니다.
- 검증 대상 커밋에서 `app` 검증 APK와 계측 테스트 APK를 빌드합니다.

## 검증 실행 구조

### 통합 테스트 위치

- 테스트 루트: `app/src/androidTest/java/kr/open/library/simpleui_xml/deviceverification/`
- 공통 테스트 러너: `androidx.test.runner.AndroidJUnitRunner`
- 모듈별 권장 패키지:
  - `deviceverification.core`
  - `deviceverification.systemmanager`
  - `deviceverification.compose`
  - `deviceverification.xml`
- 라이브러리 모듈 내부에 흩어진 별도 계측 앱을 만들지 않고, 네 모듈을 함께 의존하는 `app`을 실제 소비자 통합 지점으로 사용합니다.

### 기본 실행 명령

```powershell
adb devices -l
.\gradlew.bat :app:connectedDebugAndroidTest
```

- 1단계의 자동 통합 테스트는 CI가 아니라 로컬에 연결된 `PHY-01`에서 실행합니다.
- 전체 실행 전에 모듈별 테스트 필터를 사용할 수 있으나, 릴리스 승인 시에는 1단계 필수 범위 전체를 실행해야 합니다.
- Gradle이 생성한 HTML/XML 계측 테스트 결과 위치를 릴리스 결과 문서에 기록합니다.
- 자동 테스트가 통과한 뒤 수동 및 혼합 시나리오를 실행합니다.

### 검증 아티팩트 구분

- `AUTO_DEVICE`는 대상 커밋에서 생성한 debug 앱 APK와 debug 계측 테스트 APK로 실행합니다.
- `MANUAL_DEVICE`는 원칙적으로 대상 커밋에서 로컬로 생성하고 `PHY-01`에 설치한 verification APK로 실행합니다.
- `HYBRID_DEVICE`가 계측 테스트를 사용하면 debug 앱 APK를, 샘플 앱 직접 조작을 사용하면 verification APK를 사용하고 실제 사용한 빌드 유형을 기록합니다.
- 체크리스트에서 ADB로 직접 실행하는 수동 검증 Activity는 verification source set에서만 `exported=true`로 재정의하며, debug·release APK에서는 외부 비공개 상태를 유지합니다.
- verification APK는 실기기 검증 전용 아티팩트이며 게시·배포 대상에 포함하지 않습니다.
- 각 APK의 SHA-256은 서로 같아야 한다는 뜻이 아니라, 각 파일의 해시와 빌드 대상 소스 커밋이 결과 문서에서 추적되어야 한다는 뜻입니다.
- 게시 대상 라이브러리는 검증 대상 소스 커밋에서 빌드해야 합니다. 결과 기록을 추가하는 문서 전용 커밋은 검증 대상 소스 커밋과 별도로 추적할 수 있습니다.

### 검증 방식

| 방식 | 의미 | 적용 기준 |
| --- | --- | --- |
| `AUTO_DEVICE` | 계측 테스트가 동작과 결과를 자동 판정 | API 반환값, 상태 변화, 생명주기 및 UI 의미 구조를 안정적으로 판정할 수 있는 경우 |
| `MANUAL_DEVICE` | 테스터가 조작하고 화면·하드웨어 반응을 판정 | 시스템 설정 화면, 실제 진동, 키보드, 알림 표시처럼 사람의 관찰이 필요한 경우 |
| `HYBRID_DEVICE` | 계측 또는 샘플 앱이 동작을 준비하고 테스터가 최종 반응을 판정 | 알림 클릭, 알람 발화, 권한 화면 복귀 등 자동화와 관찰을 함께 사용하는 경우 |

- `HYBRID_DEVICE`는 자동 부분과 수동 부분을 각각 판정하며, 두 결과가 모두 `PASS`일 때만 최종 결과를 `PASS`로 기록합니다.
- 테스트 메서드명에 시나리오 ID가 있더라도 자동 테스트가 시나리오 전체 계약을 검증한다는 뜻은 아닙니다. 체크리스트에 정의된 수동 부분이 남아 있으면 최종 판정 전 반드시 실행합니다.
- `AUTO_DEVICE`는 수동 결과를 `N/A`, `MANUAL_DEVICE`는 자동 결과를 `N/A`로 기록합니다.

## 도입 순서와 단계 완료 조건

검증 체계는 아래 순서로 도입합니다.

1. `simple_core`
2. `simple_system_manager`
3. `simple_compose`
4. `simple_xml`

각 단계는 다음 조건을 모두 만족해야 완료할 수 있습니다.

- 해당 모듈의 P0 시나리오가 테스트 또는 체크리스트로 구현되어 있습니다.
- 실행 결과와 증빙을 Markdown 결과 형식으로 기록할 수 있습니다.
- P1 환경 미보유 항목의 예외 승인 절차를 적용할 수 있습니다.
- 테스트가 변경한 단말 상태를 복구할 수 있습니다.
- 선행 단계의 필수 검증이 계속 통과합니다.

단계 완료는 해당 모듈만 즉시 릴리스 차단한다는 뜻이 아닙니다. 네 모듈이 모두 완료되고 차단 활성화 조건을 충족한 시점부터 프로젝트 전체 릴리스 게이트로 적용합니다.

## 시나리오 우선순위

### P0: 릴리스 필수

- 지원 환경에서 핵심 공개 동작이 안전하게 실행되는지 확인합니다.
- 모든 릴리스 후보에서 실행해야 합니다.
- 결과는 `PASS`여야 하며 `FAIL`, `BLOCKED`, `ENV_UNAVAILABLE`, `NOT_RUN`은 릴리스를 차단합니다.
- P0는 환경 미보유 예외로 승인할 수 없습니다. 현재 환경에서 실행할 수 없는 항목은 차단 정책 활성화 전에 P0 범위 또는 테스트 환경을 조정해야 합니다.

### P1: 조건부 필수

- 해당 하드웨어나 기능을 사용할 수 있을 때 반드시 실행합니다.
- 실행 결과가 `FAIL`이면 릴리스를 차단합니다.
- 환경이 실제로 없을 때만 `ENV_UNAVAILABLE`로 기록하고 릴리스별 예외 승인을 받을 수 있습니다.
- 예외 승인은 해당 릴리스에만 유효하며 다음 릴리스에서 다시 승인해야 합니다.

### P2: 확장 검증

- 추가 환경, 회귀 탐색 또는 호환성 확대를 위한 항목입니다.
- 미실행 또는 환경 미보유는 릴리스를 차단하지 않습니다.
- 실패하면 이슈와 영향 범위를 기록하며, 유지보수자가 공개 API의 중대한 회귀로 판단하면 P0 또는 P1로 승격할 수 있습니다.

## 결과 상태

| 상태 | 의미 | 릴리스 판정 |
| --- | --- | --- |
| `PASS` | 기대 결과를 충족함 | 통과 |
| `FAIL` | 실행했으나 기대 결과를 충족하지 못함 | P0·P1 차단 |
| `BLOCKED` | 테스트 코드, APK, 계정 또는 절차 문제로 판정까지 진행하지 못함 | P0·P1 차단 |
| `ENV_UNAVAILABLE` | 필요한 단말·SIM·하드웨어 환경이 존재하지 않음 | P0 차단, P1은 승인된 예외 필요, P2 비차단 |
| `NOT_RUN` | 아직 실행하지 않음 | P0·P1 차단 |
| `OUT_OF_SCOPE` | 이번 릴리스의 변경 및 정해진 실행 조건상 적용 대상이 아님 | 적용 근거가 타당할 때 비차단 |

- 기능 실패를 `ENV_UNAVAILABLE`로 바꾸어 기록해서는 안 됩니다.
- 권한 거부, 네트워크 끊김처럼 시나리오가 의도한 상태는 환경 미보유가 아니라 정상 테스트 조건입니다.
- `OUT_OF_SCOPE`는 시나리오에 사전에 정의된 적용 조건이 맞지 않을 때만 사용합니다. 실행하기 어렵다는 이유로 사용할 수 없습니다.

### 사전 상태 불일치 처리

- 각 시나리오는 실행 전에 권한, Wi-Fi, 위치 및 시스템 설정의 사전 상태를 확인합니다.
- 사전 상태를 안전하게 변경하고 복구할 수 있으면 변경 전 값을 기록한 뒤 테스트 조건으로 맞추고, 종료 후 원래 상태로 복구합니다.
- 사전 상태를 맞출 수 없어 기대 동작을 판정하지 못하면 기능 실패인 `FAIL`이 아니라 절차 미완료인 `BLOCKED`로 기록합니다. P0·P1의 `BLOCKED`는 릴리스를 차단합니다.
- P0 자동 테스트는 사전 조건 불일치를 JUnit skip으로 통과시켜서는 안 됩니다. 시나리오 ID, 기대 상태, 실제 상태 및 `DeviceEnvironmentSnapshot`에 해당하는 단말 정보를 실패 메시지에 남깁니다.
- 1단계 `PHY-01`의 권한 복귀 시나리오는 오버레이 권한이 꺼진 상태, Wi-Fi 연결 시나리오는 Wi-Fi가 켜지고 연결된 상태를 기본 사전 조건으로 사용합니다.

## 시나리오 공통 규격

각 시나리오는 다음 항목을 포함해야 합니다.

- 시나리오 ID
- 대상 모듈과 공개 기능
- 우선순위
- 검증 방식
- 적용 조건과 사전 상태
- 실행 절차
- 기대 결과
- 정리·복구 절차
- 필요한 증빙
- 실패 시 기록할 진단 정보

시나리오 ID는 문서와 테스트 코드에서 동일하게 사용합니다. 테스트 메서드명 또는 `@DisplayName`에 시나리오 ID를 포함하여 자동 결과와 Markdown 기록을 연결합니다.

## 1단계 최소 시나리오

아래 표는 차단 정책 활성화 전에 구현해야 하는 최소 검증 범위입니다. 세부 테스트 데이터와 UI 선택자는 IMPLEMENTATION_PLAN 및 구현 단계에서 현재 샘플 앱 구조에 맞게 확정합니다.

### `simple_core`

| ID | 우선순위 | 방식 | 검증 내용 | 기대 결과 |
| --- | --- | --- | --- | --- |
| `CORE-P0-001` | P0 | `AUTO_DEVICE` | 앱 Context가 필요한 core 공개 API의 소비자 통합 | 명시적 초기화 없이 소비자 앱에서 접근하고 규격화된 결과를 반환함 |
| `CORE-P0-002` | P0 | `AUTO_DEVICE` | 일반 권한의 허용·거부 상태 판정 | 실제 PackageManager 상태와 라이브러리 판정이 일치 |
| `CORE-P0-003` | P0 | `HYBRID_DEVICE` | 특수 권한 설정 이동 후 앱 복귀 및 상태 재판정 | 복귀 시 최신 권한 상태를 반영하고 요청 흐름이 중복 완료되지 않음 |
| `CORE-P0-004` | P0 | `AUTO_DEVICE` | SharedPreferences 저장·조회·삭제 | 동일 앱 프로세스와 재생성 후 값이 규격대로 유지·삭제됨 |
| `CORE-P1-001` | P1 | `HYBRID_DEVICE` | Logx 파일 출력과 앱 재실행 후 기록 확인 | 설정한 경로·필터·형식에 맞는 로그 파일과 내용이 생성됨 |

- `CORE-P1-001`의 자동 범위는 실제 파일 생성, 파일명·라인 포맷, 로그 타입 허용 목록, 태그 차단 목록 및 테스트 파일 정리입니다.
- `CORE-P1-001`의 수동 범위는 verification 앱에서 사용자 지정 경로에 로그 파일을 생성하고, 앱 프로세스 종료·재실행 후 기존 파일이 유지되는지 확인하는 것입니다.

### `simple_system_manager`

| ID | 우선순위 | 방식 | 검증 내용 | 기대 결과 |

- 알림 테스트는 생성한 알림을 모두 취소합니다.

## 결과 기록 규격

### 문서 위치

- 공통 템플릿: `docs/verification/device/DEVICE_TEST_RESULT_TEMPLATE.md`
- 릴리스 결과: `docs/verification/device/releases/{version}/DEVICE_TEST_RESULT.md`
- 스크린샷·로그 등 증빙: `docs/verification/device/releases/{version}/evidence/`

위 경로의 템플릿과 결과 문서는 구현 단계에서 추가합니다. 릴리스별 결과는 이전 릴리스 문서를 덮어쓰지 않습니다.

### 필수 메타데이터

- 릴리스 버전
- 검증 대상 소스 Git 커밋 SHA
- 결과 문서를 저장한 Git 커밋 SHA
- 검증 APK 파일명과 SHA-256
- debug 앱 APK 파일명과 SHA-256
- 테스트 APK 파일명과 SHA-256
- 게시 대상 라이브러리의 빌드 소스 커밋 SHA
- 검증 일시와 시간대
- 테스터와 승인자
- 단말 슬롯, 제조사·모델, Android/API, ABI, 보안 패치 수준
- SIM, Wi-Fi, 위치, 배터리 및 절전 모드 상태
- 자동 테스트 명령, 종료 상태 및 Gradle 결과 경로

### 시나리오 결과 표

각 릴리스 결과 문서는 최소한 다음 열을 포함합니다.

| 시나리오 ID | 우선순위 | 방식 | 자동 결과 | 수동 결과 | 최종 결과 | 증빙 | 이슈 | 예외 승인 ID | 비고 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

- `HYBRID_DEVICE`의 자동·수동 결과 중 하나라도 `FAIL`, `BLOCKED`, `NOT_RUN`이면 최종 결과를 `PASS`로 기록하지 않습니다.
- 자동 또는 수동 결과가 `PASS` 이외이면 원인과 재현 정보를 작성합니다.
- 수동 및 혼합 시나리오는 화면 캡처, 로그 또는 관찰 기록 중 하나 이상의 증빙을 남깁니다.
- 자동 시나리오는 Gradle 결과와 테스트 이름으로 추적할 수 있어야 합니다.
- 사전 조건 자동 실패 메시지는 시나리오 ID, 기대값, 실제값과 관련 단말 환경을 포함해야 합니다.
- 민감한 전화번호, 계정, 토큰 및 위치 원본은 증빙에 포함하지 않습니다.

### 최종 판정 항목

- P0 전체 개수와 상태별 개수
- P1 전체 개수, 환경 미보유 개수 및 승인된 예외 개수
- P2 실행 개수와 발견 이슈
- 남은 `FAIL`, `BLOCKED`, `NOT_RUN`
- 단말 상태 복구 확인
- 대상 커밋·아티팩트 일치 확인
- 최종 판정: `APPROVED` 또는 `REJECTED`
- 승인자, 승인 일시 및 승인 근거

개인 프로젝트 운영 중에는 테스터와 승인자가 동일할 수 있지만 두 역할과 확인 시점은 별도 필드로 기록합니다.

## 환경 미보유 예외 승인

### 허용 조건

- P1 시나리오에 필요한 물리 환경이 존재하지 않습니다.
- 현재 보유 환경만으로 대체 검증할 수 없습니다.
- 해당 항목의 미검증 위험과 완화 수단을 문서화합니다.
- 유지보수자가 해당 릴리스에 한해 위험을 수용합니다.

### 금지 조건

- P0 시나리오
- 실행 결과가 이미 `FAIL`인 시나리오
- 테스트 코드 또는 APK 문제로 실행하지 못한 `BLOCKED` 상태
- 시간 부족이나 절차 누락으로 실행하지 않은 `NOT_RUN` 상태

### 예외 기록 필드

- 예외 승인 ID
- 릴리스 버전과 커밋 SHA
- 시나리오 ID
- 필요한 환경과 미보유 사유
- 영향받는 공개 API와 사용자 위험
- 대체 검증 또는 완화 조치
- 승인자와 승인 일시
- 만료 릴리스

예외 승인은 승인된 릴리스가 종료되면 만료됩니다. 같은 환경이 다음 릴리스에도 없으면 기존 예외를 복사해 자동 승인하지 않고, 최신 코드와 위험을 기준으로 다시 승인합니다.

## 릴리스 상태와 차단 규칙

### 검증 상태

| 상태 | 의미 |
| --- | --- |
| `DRAFT` | 대상 커밋과 검증 계획이 작성됨 |
| `TESTING` | 자동·수동 검증을 실행 중임 |
| `EXCEPTION_REVIEW` | P1 환경 미보유 예외를 검토 중임 |
| `APPROVED` | 모든 차단 조건을 충족함 |
| `REJECTED` | 실패 또는 미완료 항목으로 릴리스할 수 없음 |

### `APPROVED` 조건

- debug 앱 APK, 검증 APK 및 테스트 APK의 SHA-256이 각각 기록되어 있고 빌드 출처가 검증 대상 소스 커밋을 가리킵니다.
- 게시 대상 라이브러리의 빌드 소스 커밋이 검증 대상 소스 커밋과 일치합니다.
- 모든 P0가 `PASS`입니다.
- 모든 적용 대상 P1이 `PASS`이거나 해당 릴리스에 유효한 예외 승인을 받았습니다.
- P0·P1에 `FAIL`, `BLOCKED`, `NOT_RUN`이 없습니다.
- 필수 메타데이터와 증빙이 Markdown 결과에 기록되어 있습니다.
- 테스트가 변경한 단말 상태가 복구되었습니다.
- 승인자가 최종 판정과 일시를 기록했습니다.

### 승인 무효화

- 승인 이후 검증 대상 소스 커밋의 제품 코드, 빌드 설정 또는 배포 설정이 변경되면 기존 승인은 무효입니다.
- APK 또는 라이브러리 아티팩트를 다시 빌드해 내용이 달라지면 SHA-256을 갱신하고 영향을 받는 검증을 다시 수행합니다.
- 결과 문서만 추가·수정한 문서 전용 커밋은 검증 대상 소스 커밋을 바꾸지 않습니다. 이 경우 승인 이력을 보존하고 결과 문서 커밋과 변경 사유를 별도로 기록합니다.

## 릴리스 차단 활성화 조건

다음 조건을 모두 충족한 이후에만 실기기 검증을 GitHub Release 및 Maven Central 게시의 필수 선행 조건으로 활성화합니다.

- 네 모듈의 1단계 최소 시나리오가 구현되어 있습니다.
- `:app:connectedDebugAndroidTest`가 `PHY-01`에서 실행됩니다.
- 수동·혼합 시나리오 체크리스트와 복구 절차가 준비되어 있습니다.
- 공통 결과 템플릿과 릴리스별 저장 경로가 준비되어 있습니다.
- P1 환경 미보유 예외 승인 형식이 준비되어 있습니다.
- 검증 APK와 게시 아티팩트를 동일 커밋으로 연결할 수 있습니다.
- GitHub Actions가 실기기 테스트를 실행하지 않고 승인된 커밋인지 확인하는 배포 진입 조건을 적용할 계획이 승인되어 있습니다.
- 기존 GitHub Release와 Maven Central 게시 작업의 내부 순서를 바꾸지 않고, 승인 전 자동 게시를 방지할 수 있습니다.

활성화 전에는 기존 릴리스 흐름을 유지합니다. 활성화 이후 `APPROVED`가 아닌 릴리스 후보는 GitHub Release 및 Maven Central 게시를 진행할 수 없습니다.

## 구현 계획 입력 항목

IMPLEMENTATION_PLAN은 다음 작업의 순서, 파일 단위 변경, 검증 명령 및 롤백 기준을 정의해야 합니다.

- `app/src/androidTest` 공통 하네스와 모듈별 테스트 추가
- Compose UI 계측 테스트에 필요한 `androidTest` 의존성 추가
- 샘플 앱의 테스트 진입점과 안정적인 UI 식별자 보완
- 수동·혼합 체크리스트 및 Markdown 결과 템플릿 추가
- 검증 APK와 테스트 APK의 커밋·해시 기록 절차 추가
- 네 모듈 도입 순서에 따른 단계별 실행과 회귀 검증
- 로컬 실기기 승인 결과와 대상 커밋을 확인하는 수동 CD 진입 게이트 추가
- 2단계 에뮬레이터 및 CI 자동화 분리 계획
