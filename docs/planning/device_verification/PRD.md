# 실기기 검증 체계 PRD

## 문서 정보

- 문서명: 실기기 검증 체계 PRD
- 대상 프로젝트: Simple UI
- 대상 모듈: `simple_core`, `simple_system_manager`, `simple_compose`, `simple_xml`, `app`
- 상태: Draft
- 연계 문서: [SPEC.md](./SPEC.md)
- 연계 문서: [IMPLEMENTATION_PLAN.md](./IMPLEMENTATION_PLAN.md)

## 배경

Simple UI는 Unit 테스트, Robolectric 테스트, API 호환성 검사, 정적 분석 및 빌드 검증을 통해 JVM 기반 품질 검증 체계를 운영하고 있습니다.

하지만 실제 Android 기기에서만 확인할 수 있는 제조사별 동작, 시스템 서비스 상태, 권한 화면 복귀, 백그라운드 제한, 네트워크·SIM·위치·진동과 같은 하드웨어 의존 동작은 현재 릴리스 승인 기준에 포함되어 있지 않습니다.

샘플 앱은 주요 기능을 직접 실행할 수 있는 화면을 제공하고 Firebase App Distribution을 통해 검증 APK를 배포할 수 있습니다. 그러나 검증 대상 기기, 필수 시나리오, 통과 기준, 결과 기록 형식 및 릴리스 차단 규칙이 체계화되어 있지 않아 실제 검증 결과가 Maven Central 게시 여부를 결정하지 못합니다.

## 현재 상태

- `simple_core`, `simple_system_manager`, `simple_compose`, `simple_xml`에는 유효한 `androidTest`가 없습니다.
- `app`의 계측 테스트는 애플리케이션 패키지명만 확인하는 기본 예제 수준입니다.
- 실기기 수동 테스트 항목은 일부 샘플 화면에만 분산되어 있습니다.
- CI는 Unit 테스트와 Robolectric 테스트를 실행하지만 에뮬레이터 또는 실기기 계측 테스트를 실행하지 않습니다.
- Firebase App Distribution으로 검증 APK를 전달할 수 있지만 결과를 기록하고 승인하는 공통 절차가 없습니다.
- 현재 CD는 Maven Central 게시 이후에 Firebase App Distribution을 수행하므로 실기기 검증이 릴리스 차단 조건으로 작동하지 않습니다.

## 문제 정의

- 실제 기기에서만 발생하는 제조사·OS·하드웨어 차이를 릴리스 전에 발견한다고 보장할 수 없습니다.
- Robolectric 성공 결과만으로 시스템 서비스와 UI 생명주기의 실제 동작을 보증하기 어렵습니다.
- 어떤 기기와 API에서 무엇을 검증했는지 추적할 수 없습니다.
- 검증 실패, 실행 불가 및 조건부 승인에 대한 공통 판정 기준이 없습니다.
- 검증한 APK와 실제 게시되는 라이브러리가 동일한 커밋인지 보장하는 절차가 없습니다.
- 실기기 검증 실패가 GitHub Release와 Maven Central 게시를 차단하지 못합니다.

## 목표

- 릴리스 후보에 대해 반복 가능하고 증빙 가능한 실기기 검증 체계를 정의합니다.
- 모듈과 기능별로 자동 계측 테스트와 수동 실기기 테스트의 책임을 구분합니다.
- 1단계에서는 보유 실기기를 중심으로 현실적인 최소 검증 환경을 정의하고, 이후 단계에서 에뮬레이터와 CI 자동화를 보완합니다.
- 기능별 필수 시나리오, 결과 기록 및 예외 승인 기준을 마련합니다.
- 검증 APK와 게시 대상 라이브러리를 동일한 커밋으로 연결합니다.
- 검증 체계가 준비된 이후에는 필수 실기기 검증 실패가 릴리스를 차단하도록 합니다.
- 제한된 기기 환경에서도 지속적으로 운영 가능한 절차를 구축합니다.

## 비목표

- 모든 Android API, 제조사, 모델 및 통신사 조합을 전수 검증하지 않습니다.
- Unit 테스트와 Robolectric 테스트를 실기기 테스트로 대체하지 않습니다.
- 모든 하드웨어 의존 시나리오를 자동화하지 않습니다.
- 초기 단계에서 유료 기기 팜 또는 Firebase Test Lab을 필수로 도입하지 않습니다.
- 모든 일반 PR에 수동 실기기 검증을 요구하지 않습니다.
- 현재 사용할 수 없는 실제 SIM·멀티 SIM 환경을 검증 완료로 간주하지 않습니다.
- 1단계에서 에뮬레이터 매트릭스와 CI 계측 테스트를 릴리스 차단 조건으로 도입하지 않습니다.
- 이번 PRD에서 개별 테스트 코드와 CI/CD 구현 방법을 확정하지 않습니다.

## 대상 사용자

- 라이브러리를 개발하고 릴리스하는 유지보수자
- Firebase App Distribution으로 릴리스 후보를 검증하는 테스터
- Maven Central 또는 JitPack에서 라이브러리를 사용하는 Android 개발자
- 실기기 회귀 여부와 릴리스 근거를 확인하는 협업자

## 적용 범위

### `simple_core`

- 권한 상태 판정
- 파일·로그·로컬 저장소와 Android Context 연동
- 라이프사이클 및 메인 스레드 의존 동작
- 다른 라이브러리 모듈이 공통으로 사용하는 기반 기능

### `simple_system_manager`

- 알람, 알림, 진동, Wi-Fi
- 배터리, 위치, 전화망, SIM, 네트워크 연결 상태
- 시스템 바, 소프트키보드, 플로팅 윈도우, 화면 정보
- 실제 OS 정책과 제조사 구현 차이에 영향을 받는 시스템 기능

### `simple_compose`

- Compose 화면 진입과 렌더링
- Compose 생명주기 및 라이브러리 기본 구성
- XML 모듈에 확대 적용하기 전 계측 테스트 패턴 검증

### `simple_xml`

- Activity, Fragment, DialogFragment 생명주기
- DataBinding, ViewBinding, RecyclerView 및 View 확장
- 일반 권한과 특수 권한 요청·복귀 흐름
- 실제 Window, 인셋, 키보드 및 사용자 상호작용

### 검증 애플리케이션 및 운영 환경

- `app` 샘플 화면과 검증용 APK
- 연결된 실기기에서 실행하는 `app/src/androidTest` 통합 테스트
- 로컬 설치한 verification APK 기반 실기기 수동 검증
- 필요할 경우 Firebase App Distribution을 이용한 보조 배포
- GitHub Actions 릴리스 승인 및 Maven Central 게시 흐름

## 단계별 적용 범위

### 1단계: 실기기 중심 검증

- 현재 연결 가능한 전용 테스트 단말에서 자동 통합 테스트와 수동 시나리오를 실행합니다.
- 네 라이브러리 모듈의 실기기 검증 범위를 도입 순서에 따라 확립합니다.
- 검증 결과와 예외 승인을 Markdown 문서로 기록합니다.
- 네 모듈의 실행·기록·승인 체계가 모두 준비된 뒤 릴리스 차단 정책을 활성화합니다.

### 2단계: 에뮬레이터 및 CI 자동화 보완

- minSdk와 주요 플랫폼 정책 변경 구간을 포함하는 에뮬레이터 매트릭스를 도입합니다.
- CI에서 자동 계측 테스트를 실행하고 결과를 릴리스 검증 기록과 연결합니다.
- 필요할 경우 추가 제조사 단말, 외부 테스터 또는 기기 팜으로 검증 범위를 확장합니다.

## 검증 체계 도입 순서

검증 체계는 다음 순서로 도입합니다.

1. `simple_core`
2. `simple_system_manager`
3. `simple_compose`
4. `simple_xml`

### 순서 결정 근거

- `simple_core`는 모든 라이브러리 모듈의 기반이므로 공통 검증 기준을 먼저 확립합니다.
- `simple_system_manager`는 실제 하드웨어, OS 정책 및 제조사 차이에 가장 크게 영향을 받으므로 기반 확립 직후 검증합니다.
- `simple_compose`는 현재 메인 코드 범위가 작아 계측 테스트와 체크리스트 구조를 비교적 빠르게 검증하고 완료할 수 있습니다.
- `simple_xml`은 기능과 파일 범위가 가장 크므로 앞선 모듈에서 확립한 패턴을 재사용하여 마지막 단계에서 체계적으로 적용합니다.

이 순서는 단순 위험도 순위가 아니라 기반성, 실기기 위험, 작업량 및 검증 패턴 재사용 가능성을 함께 고려한 실행 순서입니다. 각 모듈의 필수 시나리오 수와 검증 깊이는 SPEC에서 별도로 정의합니다.

## 검증 환경 원칙

- 현재 보유한 Android 실기기를 주 검증 기기로 사용합니다.
- 1단계는 실기기 검증에 집중하고, minSdk와 주요 플랫폼 정책 변경 구간의 에뮬레이터 보완은 2단계에서 수행합니다.
- 초기 단계에서는 유료 기기 팜을 필수로 도입하지 않습니다.
- 모든 제조사와 하드웨어 구성을 전수 검증하지 않고 위험 기반 최소 매트릭스를 운영합니다.
- 정확한 기기 슬롯, 현재 할당 기기, API 매트릭스 및 필수 여부는 SPEC에서 정의합니다.

## SIM 및 전화망 검증 정책

- 현재 기기에서 SIM이 없는 상태의 안전한 fallback 동작을 필수로 검증합니다.
- 실제 SIM 또는 멀티 SIM 환경이 필요한 검증은 환경 미보유 상태와 예외 승인을 구분하여 관리합니다.
- 추가 실기기 또는 외부 테스터 환경이 확보되면 실제 SIM 검증을 필수 범위로 확장할 수 있습니다.
- 구체적인 시나리오, 판정 상태 및 예외 승인 조건은 SPEC에서 정의합니다.

## 릴리스 차단 정책

### 일반 변경 및 PR

- Unit 테스트, Robolectric 테스트, API 검사, 정적 분석 및 빌드 검증을 필수로 수행합니다.
- 1단계의 자동 계측 테스트는 필요할 때 연결된 실기기에서 수행하고, CI 에뮬레이터 자동화는 2단계에서 도입합니다.
- 모든 PR에 수동 실기기 검증을 요구하지 않습니다.

### 릴리스 후보

- 검증 체계 활성화 이후에는 Maven Central 게시 전에 필수 실기기 검증을 수행합니다.
- 필수 시나리오 중 하나라도 실패하면 릴리스를 차단합니다.
- 실기기 검증 승인 이후에만 GitHub Release와 Maven Central 게시를 진행합니다.
- 실기기 검증은 로컬에 연결된 전용 단말에서 수행하고, GitHub Actions는 승인된 대상 커밋인지 확인하는 배포 진입 조건만 담당합니다.
- 실패, 실행 불가 및 예외 승인에 대한 세부 판정은 SPEC을 따릅니다.

### 차단 정책 활성화 시점

- 네 라이브러리 모듈의 검증 범위와 실행·기록·승인 절차가 준비된 이후 차단 정책을 활성화합니다.
- 검증 체계가 준비되기 전까지는 기존 릴리스 흐름을 유지합니다.
- 정확한 활성화 조건과 전환 절차는 SPEC과 IMPLEMENTATION_PLAN에서 정의합니다.

## 핵심 제품 요구사항

- 각 기능을 JVM, 자동 계측 또는 수동 실기기 검증 대상으로 분류해야 합니다.
- 실제 하드웨어나 제조사 동작이 필요한 기능은 Robolectric 성공만으로 릴리스 승인하지 않아야 합니다.
- 사용자 상태를 변경하는 검증은 사전 조건과 복구 방법을 제공해야 합니다.
- 검증 결과는 릴리스 버전과 대상 커밋에 연결되어 추적 가능해야 합니다.
- 검증 APK와 게시 대상 라이브러리는 동일한 커밋에서 생성되어야 합니다.
- 실패와 예외 승인은 릴리스 후에도 확인 가능한 근거를 남겨야 합니다.
- 결과 상태, 기록 항목, 승인 주체 및 릴리스 상태 전이는 SPEC에서 정의합니다.

## 성공 기준

- 네 라이브러리 모듈의 필수 실기기 검증 범위가 정의됩니다.
- 모든 릴리스 후보에 버전 및 커밋과 연결된 검증 결과가 존재합니다.
- 검증 결과가 재현 및 추적 가능한 형태로 관리됩니다.
- 1단계의 자동화 가능한 핵심 시나리오는 연결된 실기기에서 실행하는 `app/src/androidTest` 통합 테스트로 전환됩니다.
- 2단계에서는 에뮬레이터와 CI 자동 검증 범위가 정의됩니다.
- 실기기 전용 시나리오는 재사용 가능한 체크리스트로 운영됩니다.
- SIM 없음 fallback과 실제 SIM 환경 미보유 상태가 구분됩니다.
- 차단 정책 활성화 이후에는 필수 검증 실패 상태에서 GitHub Release와 Maven Central 게시가 진행되지 않습니다.
- 검증 APK와 게시 대상 라이브러리가 동일한 커밋에서 생성됩니다.

## 제약 조건

- 현재 즉시 사용할 수 있는 실기기는 Samsung Android 12 기기 한 대입니다.
- 현재 기기에는 SIM이 없어 실제 SIM 및 전화망 데이터 검증이 제한됩니다.
- 초기 도입 단계에서는 유료 기기 팜을 사용하지 않습니다.
- 수동 검증 비용을 고려하여 모든 PR이 아니라 릴리스 후보에 집중합니다.
- 권한, 설정 화면, 백그라운드 및 하드웨어 시나리오는 완전 자동화가 어려울 수 있습니다.

## 위험과 대응 방향

### 제한된 기기 구성

- 위험: 한 제조사와 한 API의 성공 결과를 전체 Android 환경의 성공으로 오인할 수 있습니다.
- 대응: 1단계 결과에 단말 한계를 명시하고, 2단계에서 minSdk와 주요 플랫폼 정책 변경 구간의 에뮬레이터 및 추가 기기 확보 여부에 따라 매트릭스를 확장합니다.

### 수동 검증 누락 또는 형식적 수행

- 위험: 결과 기록 없이 구두 확인만으로 릴리스가 승인될 수 있습니다.
- 대응: 필수 체크리스트와 승인 기록을 릴리스 차단 조건으로 사용합니다.

### 검증 APK와 게시 커밋 불일치

- 위험: 검증하지 않은 코드가 게시될 수 있습니다.
- 대응: 커밋 SHA와 아티팩트 정보를 검증 결과에 포함하고 동일 커밋만 게시합니다.

### 실기기 테스트 비용 증가

- 위험: 릴리스 속도가 불필요하게 느려질 수 있습니다.
- 대응: PR 단계는 자동 검증을 유지하고 수동 실기기 검증은 릴리스 후보에만 적용합니다.

### 하드웨어 미보유

- 위험: 실제 SIM 또는 특정 제조사 기능을 검증하지 못할 수 있습니다.
- 대응: 환경 미보유를 명시하고 예외 승인, 외부 테스터 또는 향후 기기 팜 도입 기준을 마련합니다.
